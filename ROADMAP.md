## Приоритет 1 — Улучшить промпт Claude ✅
**Статус:** Выполнено

**Проблема:** Claude получает слишком мало контекста — только 20 сырых OHLCV-свечей и 4 числа OBD. Без вычисленных метрик модель не может адекватно оценить рыночную ситуацию.

**Решение:**
- Вычислять RSI(14) из свечей на бэкенде перед вызовом Claude
- Передавать объёмный тренд (растёт / падает за последние 5 свечей, %)
- Передавать направление последних 3 candle bodies (bullish/bearish/doji)
- Передавать ATR(14) для контекста волатильности
- Добавить в системный промпт чёткие правила интерпретации этих метрик

## Приоритет 2 — Фильтр сигналов по confidence ✅
**Статус:** Выполнено

**Проблема:** Telegram-уведомление уходит на любой не-WAIT сигнал, даже с confidence=5. Это создаёт шум и снижает доверие к сигналам.

**Решение:**
- Добавить поле `minConfidence` в таблицу `Settings` (default: 65)
- Отправлять Telegram только если `confidence >= minConfidence`
- Отображать в UI бейдж уверенности с цветовой кодировкой (красный < 50, жёлтый 50–70, зелёный > 70)

## Приоритет 3 — Multi-timeframe контекст для Claude ✅
**Статус:** Выполнено

**Проблема:** Система смотрит только на 1m свечи. Claude не знает, что происходит на старших таймфреймах — сигнал против тренда 15m должен получать низкий confidence.

**Решение:**
- Перед вызовом Claude подтягивать 20 свечей на `5m` и `15m` через Binance REST
- Передавать Claude направление тренда на каждом таймфрейме (определять по EMA или просто по положению закрытия относительно средней)
- Добавить в промпт инструкцию: сигнал против старшего тренда → понижать confidence

## Приоритет 4 — Корректная цена входа для трекинга
**Статус:** Выполнено ✅

**Проблема:** `signal.price` фиксируется в момент OBD-паттерна. Claude отвечает через 10–30 секунд — к этому времени цена меняется. Трекинг WIN/LOSS считается от некорректной цены входа.

**Решение:**
- После получения ответа от Claude (direction != WAIT) делать REST-запрос за актуальной ценой (`/api/v3/ticker/price`)
- Обновлять `signal.price` этой актуальной ценой
- Пересчитывать SL/TP с учётом нового ценового уровня (если Claude вернул относительные смещения)

## Приоритет 5 — SHORT-сигналы ✅
**Статус:** Выполнено

**Проблема:** Система детектирует только LONG (просадка OBD + отскок). В даун-трендах и боковых рынках это приводит к большому числу убыточных сигналов. Логика трекинга для SHORT уже готова.

**Решение:**
- В `engine.js` добавить детекцию инвертированного паттерна: все 4 OBD резко выросли (spike) затем начали падать → сигнал SHORT
- Добавить отдельный `dipThreshold` для SHORT или использовать тот же
- Проверить корректность P&L-расчёта в `tracker.js` для SHORT-направления

## Приоритет 6 — Бэктестинг на реальных данных
**Статус:** Частично выполнено ✅ (инфраструктура готова, данные накапливаются)

**Что сделано:**
- `ObdSnapshot` таблица — автоматически пишет снапшоты OBD каждые 30 секунд на каждую пару
- `runBacktest()` — реплей `detectSignal()` на накопленных снапшотах с настраиваемыми SL%/TP%
- `getEnhancedStats()` — аналитика по накопленным сигналам: winrate по confidence/direction/часам суток
- Вкладка **Backtest** в Stats UI: статус накопления данных, форма конфигурации, equity curve, таблица сделок
- Вкладка **Analytics** в Stats UI: heatmap по часам, LONG vs SHORT, по уровням уверенности

**Важно про накопление данных:**
- Снапшоты пишутся с момента деплоя автоматически (~23K строк/день, 4 пары по 30с)
- Таблицу `ObdSnapshot` **нельзя чистить** — это датасет для бэктеста
- После 1 недели (~160K строк) бэктест уже даёт значимые результаты
- После 1 месяца (~700K строк) — надёжная статистика по стратегии
- Индекс `(pairId, createdAt)` обеспечивает быстрые запросы даже на больших объёмах

**Что ещё можно улучшить (когда накопится 1+ месяц данных):**
- Добавить максимальную просадку (max drawdown) и Sharpe ratio в статистику бэктеста
- Оптимизатор параметров: перебор threshold/SL/TP по сетке для поиска оптимальных значений
- Сравнение нескольких конфигураций на одном графике

## Приоритет 8 — User Data Stream (трекинг исполнения ордеров)
**Статус:** Выполнено ✅

**Проблема:** Система не знает, когда реально сработал TP/SL на Binance. `tracker.js` отслеживает WIN/LOSS по рыночной цене приближённо — сравнивает текущую цену с уровнями SL/TP каждые 5 секунд. Это не отражает реальный PnL автосделок: ордер мог исполниться по другой цене (проскальзывание, частичное исполнение).

**Решение:**
- Подключить Binance User Data Stream (WebSocket `/ws/<listenKey>`)
- Слушать события `executionReport` (ORDER_UPDATE) — когда OCO-ордер срабатывает (FILLED), обновлять Trade.status = 'CLOSED', Trade.pnl = реальный PnL
- Обновлять Signal.outcome = WIN/LOSS/BREAKEVEN на основе реального исполнения, не приближённой цены
- `listenKey` нужно обновлять каждые 30 минут (`PUT /api/v3/userDataStream`)

## Приоритет 9 — WebSocket для Order Book (вместо REST-поллинга)
**Статус:** Выполнено ✅

**Проблема:** Сейчас `orderbook.js` делает REST-запрос к `data-api.binance.vision/api/v3/depth` каждые 5 секунд для каждой пары. Это создаёт rate limit нагрузку (429/418 ошибки), особенно на `data-api` который лимитируется строже чем основной API. При добавлении новых пар проблема усугубляется.

**Решение:**
- Подключить Binance WebSocket стримы `<symbol>@depth@100ms` для каждой активной пары
- WebSocket-обновления не считаются в HTTP rate limit — нет риска 429/418
- Обновления приходят каждые 100ms вместо раз в 5 секунд — более точное OBD
- Поддерживать локальный order book snapshot + применять incremental diff-апдейты по протоколу Binance
- Переиспользовать паттерн из `services/binance/websocket.js` (kline стримы уже работают так)

## Приоритет 10 — Корректная обработка SHORT на споте
**Статус:** Выполнено ✅

**Проблема:** SHORT сигнал на споте = SELL MARKET ордер. На реальном счёте это продаёт актив из портфеля (BTC, ETH и т.д.). Если актива нет — Binance вернёт ошибку `insufficient balance` и автосделка упадёт. Система фактически полезна для SHORT только если держишь все торгуемые активы на балансе постоянно.

**Решение:**
- Перед SHORT автосделкой запрашивать баланс актива (`getAccountBalance`)
- Если свободного актива меньше чем `quantity` — пропускать сделку с предупреждением в лог и Telegram
- Опционально: добавить в Settings флаг `enableShortSignals: boolean` для отключения SHORT автосделок без отключения SHORT-сигналов (чтобы они по-прежнему приходили в Telegram для ручной торговли)

## Приоритет 12 — Точность трекинга и контекст Claude (низкий приоритет)
**Статус:** Не начато

**Проблемы и решения:**

**`tracker.js` — порог BREAKEVEN без учёта комиссии**
- `outcomePnl > 0.1%` считается WIN, но после round-trip комиссии 0.2% (0.1% × 2) это фактически убыток
- Некритично — `tracker.js` считает приблизительно, реальные результаты берёт `userDataStream` по факту исполнения ордеров
- Исправление: изменить порог WIN на `> 0.3%` (0.1% profit + 0.2% fees), LOSS на `< -0.1%`, остальное BREAKEVEN

**`orchestrator.js` — Claude без контекста старших ТФ при ошибке фетча**
- Если не удаётся получить свечи 5m/15m, Claude вызывается без этих данных — анализирует неполную картину
- Сигнал проходит, но качество анализа снижается незаметно для пользователя
- Исправление: при отсутствии данных старших ТФ добавлять явное предупреждение в поле `claudeAnalysis` и в лог

## Приоритет 13 — TP/SL placement hardening

**Статус:** Не начато

Ревью потока выставления TP/SL (коммиты 41120dc..966a84d, апрель 2026) выявил ряд проблем. Сгруппированы здесь по приоритету.

### [HIGH] TP/SL-13.1: Partial success leak в `placeTpSl`

**Файл:** `backend/src/services/bybit/rest.js:306` (`placeTpSl`), `backend/src/services/indicators/engine.js:310-345` (Phase 2 retry loop)

**Проблема:**
- `placeTpSl` использует `Promise.allSettled` для параллельного создания TP и SL.
- Если одна половина успешна, а вторая отвергнута — функция бросает Error. Caller считает полную неудачу.
- Успешно созданный ордер остаётся на бирже осиротевшим.
- Phase 2 retry повторно вызывает `placeTpSl(sl, tp, ...)` с обоими уровнями → дубликат или balance-lock на уже размещённой стороне.

**Решение:** Phase 2 retry-цикл должен перечитать `getOpenOrders` и передать `null` для уже размещённой стороны — как это уже сделано в `reconcileTpSl` (engine.js:439-447). Симметричный паттерн.

**Альтернатива:** cancel orphaned order в catch-блоке `placeTpSl` перед throw. Но retry-aware передача в Phase 2 проще и консистентнее.

---

### [HIGH] TP/SL-13.2: `placeTpSl` после Market fill не учитывает fee

**Файл:** `backend/src/services/bybit/rest.js:434-445` (`placeManualOrder`), `backend/src/services/indicators/engine.js:276` (`confirmedQty = quantity`)

**Проблема:**
- Market BUY 0.001 BTC → Bybit удерживает 0.1% fee с базы → фактический баланс после филла = 0.000999 BTC.
- `placeTpSl` вызывается с исходным qty=0.001 → пытается зарезервировать 0.001 BTC для TP Limit sell → **Bybit 170131: Insufficient balance** (подтверждено в проде 2026-04-24, manual Place Order).
- То же относится к auto-trade в engine.js — `confirmedQty` берётся из запроса, не из факта исполнения.

**Решение:** после успешного Phase 1 (Market fill) читать реальный баланс базового актива через `getAccountBalance` (как это уже делается в close-trade — [portfolio.js:96-105](backend/src/routes/portfolio.js:96)), использовать `free` balance (с округлением вниз до `qtyPrecision`) как qty для `placeTpSl`.

**Проявление:** на данный момент на проде блокирует manual Place Order с SL/TP. Auto-trade тоже аффектится, но менее заметно (3 живых трейда получили SL, TP появились через Fix-кнопку уже другим путём).

### [HIGH] TP/SL-13.3: `placeTpSl` не устанавливает `orderLinkId`

**Файл:** `backend/src/services/bybit/rest.js:306` (`placeTpSl`), `backend/src/services/bybit/userDataStream.js:105-110` (handleOrderFill)

**Проблема:**
- `userDataStream.handleOrderFill` ожидает `orderLinkId.startsWith('tp-')` или `'sl-'` с суффиксом `entryOrderId` для точного маппинга exit-филла обратно к конкретному `Trade`.
- `placeTpSl` ни TP, ни SL не снабжает `orderLinkId` — всегда срабатывает fallback "match by symbol" (userDataStream.js:114-119).
- При `maxOpenTrades=1` (текущая настройка) это работает. При двух позициях на одном символе — closer попадает в случайно выбранный Trade, PnL и состояние теряются.

**Решение:**
- `placeTpSl(entryOrderId?)` — добавить опциональный параметр `entryOrderId` (сейчас в engine.js он уже известен как `entryResult.orderId`).
- Формировать `orderLinkId: 'tp-' + entrySuffix` / `'sl-' + entrySuffix`, где `entrySuffix = entryOrderId.slice(-N)` (суффикс достаточной уникальности).
- То же для `placeManualOrder`, если передаётся Market + TP/SL — использовать orderId Market-ордера.

**Связанный баг:** Emergency close (13.4) использует `cancelAllOpenOrders(symbol)` — если entrySuffix знали бы, можно было cancel только paired по `orderLinkId`.

### [HIGH] TP/SL-13.4: Emergency close отменяет ВСЕ ордера на символе

**Файл:** `backend/src/services/indicators/engine.js:351`

**Проблема:**
- При провале Phase 2 после 3 попыток вызывается `cancelAllOpenOrders(pair.tradeSymbol)` — отменит и ручные ордера пользователя, находящиеся на том же символе.
- Если пользователь держит свой Buy Limit на BTC через Place Order (или Spot UI Bybit напрямую), эмердженси-клоуз его снесёт.

**Решение:** после TP/SL-13.3 (orderLinkId) — заменить на `cancelOrderByLinkId` для каждой пары `tp-{suffix}`, `sl-{suffix}`. До того — отменять только ордера с side = exitSide (не bothSides), отфильтровав user-manual по нашему namespace orderLinkId, когда он будет.

**Priority note:** менее срочно пока `maxOpenTrades=1` и Emergency close редок, но destructive — fix-up перед увеличением частоты автоторговли.
