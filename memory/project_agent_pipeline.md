## Схема Dev→QA→TL

Три последовательных фоновых агента. Я (Claude) — координатор/шина, передаю контекст между агентами вручную.

### Агенты

**Dev (Senior Developer)**
- Читает CLAUDE.md, изучает проект
- Реализует фикс
- Пишет отчёт: что сделал, что изменил, что может быть проблемой

**QA (Tester)**
- Получает контекст: задача + отчёт Dev
- Ищет баги в реализации, edge cases, пропущенные сценарии
- Пишет отчёт: что нашёл, severity

**TL (Tech Lead)**
- Получает: задача + отчёт Dev + отчёт QA
- Финальный вердикт: BLOCKING / non-blocking
- Находит то что оба пропустили

### Реальный кейс (SEC-01, hub.js)
- Dev поставил `new URL()` до `try/catch` → необработанный TypeError на malformed URL
- QA пропустил
- TL поймал → BLOCKING → исправлено: единый try/catch на весь verifyClient

### Параллельный вариант (отложен)
Идея: queue/todo/, queue/qa/, queue/tl/ — файловая очередь, агенты работают параллельно.
Dev пишет в queue/qa/ пока QA обрабатывает предыдущий таск.
**Статус:** отложено — дорого по токенам. Вернуться когда будет бюджет.

**Why:** Хочется параллельного пайплайна без ручной координации.
**How to apply:** Использовать sequential pipeline (Dev→QA→TL) для любых нетривиальных фиксов перед коммитом.
